# ADR-0019: 用户要求在触发之外继续跟进时，用 `agent.followup()` 唤醒模型

- 状态：Accepted
- 日期：2026-10-23

## 背景

ADR-0018 去掉了等待工具，触发后本轮直接结束。这解决了「模型 sleep/轮询卡住对话」的问题，
但也留下真实场景：用户要求运行结束后继续处理（如部署、失败分析、汇报结果），
或要求关注运行中的合并冲突。
默认只发 toast 的话，模型不会在终态或冲突暂停时自动继续，用户必须再问一次（或者只能取消后才能唤醒）。

可选方案：

1. **模型自己等**：`Start-Sleep` / 循环 `cicd_status` / `schedule_create` 定时器。
   - 前两者会阻塞对话（ADR-0018 已否）；
   - `schedule_create` 只能猜时间、之后反复轮询，仍然不可靠且浪费 token。
2. **插件提供阻塞 wait**：ADR-0014 已明确否掉（长构建卡住对话）。
3. **插件在终态唤醒模型**：DSH 的 `Agent.followup()` 会排队一条下一轮 user 消息并唤醒驱动器；
   `inject()` 只加上下文不唤醒，不适合本场景。

## 决策

- `cicd_run` 新增可选参数 `followUp`（默认 `false`）。
  - 当用户诉求超出「触发」（结束后继续处理，或关注运行中的冲突/异常）时才传 `true`；
  - 触发仍立即返回，本轮照常结束，不阻塞。
- `RunWatcher` 在以下节点回调，`followUp: true` 时由 `cicd_run` 组装一条来源为 `dsh-cicd`
  的 user 角色消息并调用 `exec.agent.followup()`：
  - **终态**（`succeeded / failed`；用户主动取消除外）→ `onTerminal(record, hint)`，唤醒后继续用户交代的后续动作；
  - **首次检测到合并冲突暂停**（仍是 running）→ `onConflict(record)`，唤醒后让模型用 `cicd_conflict`
    读冲突文件/分支，和用户确认解决；每次运行只唤醒一次；
  - 冲突解决后运行继续，到终态会再按 `onTerminal` 唤醒一次（用户要求继续处理时）。
- **用户主动取消：保留 toast，不唤醒**：`cicd_cancel` 在记录上写 `canceledByUser: true`；
  watcher 仍推 `⛔` 终态 toast，但跳过 `onTerminal`（取消结果已经在工具返回里）。
  平台侧取消仍按普通终态处理。
- 唤醒消息只包含「状态/冲突、runId、progress/url/note、失败提示」；
  明确标注「这是插件自动唤醒，不是用户的新发言」，并要求模型按会话上下文继续；
  不写死「接下来做什么」，业务编排仍由模型根据用户原话决定。
- `followup` 不存在（旧 DSH）、agent 已释放、或 DSH 重启导致 watcher 丢失时，
  静默退化为只发 toast；触发输出会提示模型「当前 DSH 不支持自动唤醒」。
- 内部 `Runner.wait` 继续保留给测试/未来，不通过工具暴露。

## 后果

- 「触发 → 结束 → 继续做后续动作」可以一次请求完成，且不阻塞对话；不需要模型 sleep/轮询。
- 关注运行中冲突的请求也成立：冲突暂停时就会唤醒，不必等到用户取消（此前只能等终态）。
- 用户主动取消后仍有一条终态 toast，但不再唤醒模型，避免「刚取消又被叫醒」；
  取消结果以 `cicd_cancel` 的返回为准。
- 唤醒会产生额外模型调用和 token 消耗，因此必须显式 opt-in；默认行为仍是「只 toast」。
  一次运行最多唤醒两次：冲突暂停一次 + 终态一次。
- 唤醒消息会作为一条 `user` 角色、`source.kind = dsh-cicd` 的事件落盘，出现在会话历史里；
  模型能识别它是插件通知，不会误当成用户新指令。
- 只在当前 DSH 进程内有效：watcher 是内存态，DSH 重启后不会补唤醒；用户之后仍可用
  `cicd_status` 查状态。
- 如果用户中途改变计划，模型应在执行部署等不可逆操作前再次确认（唤醒消息里已写明）。
