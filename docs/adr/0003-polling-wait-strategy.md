# ADR-0003: 轮询等待：自适应退避、历史耗时预算、错误分级

- 状态：Accepted
- 日期：2026-10-21

## 背景

云效一次构建常见 3~5 分钟。最初的 `cicd_wait` 是固定 1.5s 轮询、最多等 120s：

- 一次 4 分钟构建会打约 160 次接口，容易撞平台限流；
- 120s 上限导致要反复调用 2~3 次；
- 平台接口报错时只是把错误塞进记录继续等，可能白等满预算；
- 用户反馈「等待时间能不能参考上一次运行耗时」以及「失败别等太久才发现」。

也评估过回调：云效只有流水线内的通知插件（要求公网可达 URL），
OpenAPI 没有事件订阅接口，DSH 也没有公网入口，所以长期只靠回调不现实。

## 决策

1. **自适应退避**：2s 起、×1.6、15s 封顶，±15% 抖动；shell 用 250ms→2s。
2. **预算**：显式 `timeoutSec` 优先；否则用同流水线上一次跑完的耗时
   `×1.25 + 20s`（60~300s）；无历史默认 180s。预算只是上限，查到终态立即返回。
3. **错误分级**：
   - 网络/超时/429/5xx → 重试；
   - 连续 4 次失败 → `gave-up`；
   - 400/401/403/404 → `fatal`，立即停止。
4. **进度**：云效 run 详情的 jobs 推断阶段，输出 `progress`。
5. **并发去重**：同一 runId 的 wait 共享一个 Promise。

## 后果

- 4 分钟构建的轮询次数从 ~160 降到 ~16；失败在下一轮（≤15s）就能发现。
- 等待结果可选（`meta.abortReason` / `errorStreak`），模型能给出可执行建议。
- 代价：首次查询立即执行，最短路径不再等固定 sleep；
  预算过长时单次工具调用会阻塞（上限 300s + 工具超时 330s）。
- 回调仍由平台通知插件负责，本插件不实现公网接收端。
